# Build decisions and open questions

Decisions made while building the first cut, where the spec was silent or where I deviated. Each one is cheap to reverse. Items marked **your call** are the ones worth a minute of your attention.

## Deviations from the spec

- **WhatsApp shows as Connected for every tenant.** The spec says only the POS (and 7shifts for two tenants) are connected. The Today page badge says "Sent to WhatsApp", so leaving WhatsApp as Available would have been incoherent in the demo. **Your call.**
- **Two ports added beyond the seven listed:** `ApprovalQueue` and `IntegrationRegistry`. The rule that pages never import fixtures directly needed a port for each. They are interfaces only.
- **Flagged shifts are front-of-house only.** Kitchen shifts are sized by prep, not covers, and flagging them made the labour list noisy. The planted Tuesdays and Friday are all FOH.
- **The orchestrator panel is computed from the run data**, not hard-coded to "4 agents, 11 steps, 1 approval pending". On a Wednesday it reads "4 agents, 13 steps, 2 approvals pending, 0 errors" because the Labour Optimizer proposes the morning after a Tuesday. Real numbers over the spec's illustrative ones.
- **Fixtures regenerate on every build** (`prebuild`). Otherwise "yesterday" goes stale the day after deploy. The generator is seeded, so the same date gives the same numbers. Set `FIXTURE_TODAY` to pin it.
- **Reorder quantity is one par**, rounded to a pack. That is what makes the spec's "40 lb chicken thigh from Sysco ($212)" come out exactly.
- **shadcn/ui components are hand-authored** in `src/components/ui` on top of Radix, following shadcn's conventions and `components.json`. The shadcn registry was unreachable from the build environment. Drop-in replacement with `npx shadcn add` works whenever you like.

## Things to decide before the first demo

- **Which tenant opens by default.** Currently Prairie Table. If the first meeting is a hotel, switch `DEFAULT_LOCATION` in `src/components/providers/app-state.tsx`.
- **Session on reload.** The spec says in-memory only, so a phone refresh sends you back to login. Any email works, so it costs ten seconds. If that will annoy you mid-demo, a one-line `sessionStorage` flag fixes it, at the cost of the spec's "memory only" rule.
- **Room service as a channel.** I added `room_service` as a fourth channel so the hotel's Today tile reads "Room service share" instead of "Delivery share". If the hotels don't think of it that way, rename the label.
- **Labour target for the hotel is 30%**, the restaurants 28%. The settings page lets you change it per tenant during the demo.

## Round two: kitchen load + a fifth tenant

Feedback from your most experienced contact drove two changes: a kitchen can get slammed by a burst of orders arriving together (not just by a busy day), and the demo needed a tenant whose rush hour isn't lunch or dinner.

- **A new ticket-count layer, separate from net sales.** Each `SalesDay` now carries `hourlyOrders` alongside the existing hourly dollar figures. This is the whole point: a burst of orders can outrun a kitchen without net sales looking unusual, so it needed its own signal rather than riding on the sales spike alert. `src/core/kitchen.ts` compares it against a location's (or a hotel outlet's) ticket-per-hour capacity.
- **Tracked hours widened from 11:00–23:00 to 07:00–23:00.** Needed to give a breakfast tenant an actual morning rush to show. This is a pure widening — every existing chart, alert and export already read the shared `HOUR_START`/`HOUR_COUNT` constants, so no page needed a rewrite. One real bug fell out of this: `hourLabel`'s default start parameter was still hard-coded to the old `11`, which silently shifted every "kitchen ran hot at HH:MM" label by four hours until the palette check caught it against the generated data.
- **The kitchen-rush hour is deterministic, not random noise.** It always lands on "yesterday," at the location's own busiest hour (or, for the Kensington Hotel, one hour all three outlets share — a hotel's dinner service, bar and room service genuinely do get busy together). Tuning it as an occasional random spike meant it only cleared the alert threshold on the tenant's naturally busiest weekdays; pinning the rush hour's ticket count to a fixed multiple of capacity makes the story show up regardless of which real-world weekday "yesterday" happens to be when someone opens the demo. **This is the same trade the spec already made for the bad Saturday and the sales spike** — legible data over strict realism — just applied to a rule you asked for after the first build.
- **New agent: Kitchen Pacing.** Mirrors how the Labour Optimizer already proposes shift changes: it evaluates yesterday's ticket load and, when it ran hot, proposes pausing delivery-app or online-order intake for 20 minutes during that rush going forward. Shows up in Agents, contributes to the orchestrator panel, and lands a real Approval.
- **The Early Bird (Banff, AB, Clover POS) is the fifth tenant** — a breakfast/brunch café, 07:00–14:30 hours, no dinner, weekend-heavy (tourist brunch). Its labour target sits at 30% rather than 28%: a short operating window with a full crew at the rush genuinely runs a higher labour percentage than a concept that spreads staff over more hours, and fighting the shift-sizing model to force it under 28% would have looked like a bug, not a fact about the concept. **Your call** if that's not the read you want a brunch-spot owner walking away with.
- **Reused the existing wage-percent calibration approach rather than hand-tuning each shift.** Widening `HOTEL_RESTAURANT_SHIFTS`' and `ROOM_SERVICE_SHIFTS`' windows to cover real breakfast hours (they previously used the 11:00–23:00 window as a rough proxy) initially pushed Kensington's labour to 39% before the per-shift sizing constants were recalibrated against the new wider windows. Landed at 29.9% for "All outlets," close to the hotel's 30% target, with more variance between individual outlets (the Grange runs a bit high, Larkspur a bit low) than before — which is itself a realistic, and arguably useful, thing for a hotel GM to see.

## Round three: monorepo split

The single Next.js app was already organized as `core`/`ports`/`adapters`, but everything ran in one process with the frontend importing adapters directly. The backend is meant to become an orchestrator connecting to different POS/vendor systems per tenant (Square, Toast, Clover, Lightspeed), so it needed to be a real, separately deployable service — not a folder convention inside the frontend.

- **Split into a Turborepo monorepo**: `apps/web` (Next.js frontend), `apps/api` (NestJS backend), `packages/contracts` (shared domain types, port interfaces, and the pure domain functions from the old `src/core`). Two separate Vercel projects, deployed and scaled independently, per the explicit call that "the backend could be deployed anywhere."
- **NestJS chosen for the backend** specifically because its module/DI system maps onto the existing ports/adapters pattern without translation: an injection token is a port, and swapping `useClass` on that token is exactly the "one line to swap a mock for a real source" story the original `src/adapters/index.ts` already told, just expressed as Nest DI instead of a plain object literal.
- **NestJS pinned to the v11 (`legacy`) line, not the v12 `latest` tag.** NestJS 12 ships as ESM-only (`"type": "module"` in `@nestjs/common`'s own `package.json`), which would have forced every relative import in `apps/api` to carry an explicit `.js` extension and complicated the Vercel Function entrypoint for no benefit here. v11 is still the actively-supported CommonJS line and cost nothing to pick.
- **`packages/contracts` exposes per-topic subpaths** (`@evolv/contracts/types`, `/format`, `/dates`, `/kitchen`, ...) via `package.json` `exports`, mirroring the old `@/core/format`-style imports almost exactly — so the import swap across ~20 frontend files was a mechanical `@/core/X` → `@evolv/contracts/X` regex, not a rewrite. A `typesVersions` block was added alongside `exports` so TypeScript's classic (non-`exports`-aware) module resolution in `apps/api` can still find the subpath type declarations; Node itself resolves the subpaths at runtime via `exports` regardless of what TypeScript's resolver mode is set to.
- **The 4 POS vendor adapters (Square, Toast, Lightspeed, Clover) are stubs, not live.** Each implements `SalesSource` with every method throwing `"not implemented — <vendor>"`, declared as files but not wired into `SalesModule`'s provider array. This keeps the demo's actual behavior (mocked, no vendor calls) unchanged while making the shape of a real integration visible for whoever picks this up next.
- **Nest's default HTTP response serialization surprised the frontend once**: a controller method returning a bare `string` (e.g. `SalesController`'s `latest-date`) comes back as `text/html` with the raw string, not `application/json` with a quoted string — Nest only JSON-serializes object/array return values. `src/lib/api-client.ts`'s `get()` helper checks the response's `content-type` and falls back to `res.text()` for non-JSON responses, so this is handled once in the client rather than needing every primitive-returning endpoint special-cased.
